# V14.1 — FPS / Hz

Le préfixe série devient :

```text
[20:36:14][ 25%:  0%:  3%][FPS: 42][Hz: 43] ...
```

## Définitions

- **FPS** = trames utiles composées par seconde. Les trames dont le seul motif est
  l'horloge système ne sont pas comptées.
- **Hz** = cadence effective de trames du compositeur Bouchaud, toutes trames
  confondues.
- **target_hz** = plafond théorique dérivé de `PERIODE_TRAME_MS`. La politique
  actuelle de 16 ms correspond à 62,5 Hz.

Le BGA QEMU ne fournit pas encore de vblank/EDID fiable à Bouchaud OS. Le `Hz`
affiché n'est donc pas le refresh physique du moniteur Windows ; il mesure ce
que **Bouchaud produit réellement**.

## Pourquoi on ne force pas encore 120 Hz

Passer immédiatement la politique de 16 ms à ~8 ms doublerait la pression sur
le compositeur alors que le run WHPX1 atteint déjà ~97 % CPU et montre des
périodes où WebContent ou Compositor occupent presque tout le vCPU. On mesure
d'abord correctement, puis on lèvera le plafond avec une horloge de trame
sub-milliseconde et le travail de rendu nécessaire.

Un bureau ou une page statique peut légitimement afficher `FPS: 0` : un système
event-driven ne doit pas redessiner 120 images identiques. La cible **120 FPS**
doit être évaluée pendant scroll, animation, déplacement de fenêtre ou entrée
continue.

## Analyse

```powershell
python .\tools\perf\analyse-fps-hz.py .\v14.1-fps.log
```

Le script déduplique les lignes par seconde pour qu'une rafale de logs ne biaise
pas la moyenne et affiche moyenne, médiane, p5, p1, seuils 30/60/90/120 FPS,
ainsi que les plus gros gaps déjà fournis par le watchdog navigateur.
